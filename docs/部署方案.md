# Hermes Agent 离线部署方案

> 面向：需要把 Hermes Agent 装到**无外网 ARM64 信创机**（Kylin V10 / UOS 20 /
> openEuler 20.03+）的场景。

---

## 1. 问题定义

官方安装方式是：

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

这个脚本会在运行时按需联网获取七类东西：

| # | 获取物 | 来源 | 离线替代 |
|---|---|---|---|
| 1 | `uv` 包管理器 | `astral.sh/uv/install.sh` | 包内 `bin/uv` |
| 2 | Python 解释器 3.11 | `uv python install`（GitHub Releases） | 包内 `runtime/cpython-3.11.*-aarch64-*.tar.gz` |
| 3 | Node.js | `nodejs.org/dist/latest-v24.x/` | 包内 `runtime/node-v*-linux-arm64.tar.xz` |
| 4 | 仓库源码 | `git clone github.com/NousResearch/hermes-agent` | 包内 `repo/hermes-agent-src.tar.gz`（按 commit 固定） |
| 5 | Python 依赖 | PyPI（`uv sync --locked`） | 包内 `wheels/` + `wheels-prebuilt/`，`pip --no-index` |
| 6 | npm 依赖 | npm registry | 包内 `node_modules/*.tar.gz`（**预构建**） |
| 7 | Chromium | Playwright CDN | 包内 `browsers/ms-playwright-arm64.tar.gz` |
| 8 | ripgrep / ffmpeg | GitHub Releases / 静态站点 | 包内 `bin/` |

外加两个 best-effort 的联网步骤（本方案不覆盖，见第 7 节）：
Browser Use CLI 和 cua-driver（Computer Use）。

---

## 2. 为什么不能直接照搬"常规离线安装"

| 常规做法 | 在本场景下为什么不行 |
|---|---|
| `pip download -r req.txt` | 在宿主平台下载 wheel。在 Windows 上给 aarch64 下，拿到的是 `win_amd64`，目标机全装不上 |
| `pip download --platform manylinux_2_28_aarch64` | 只改变"挑哪个 wheel 文件"，**依赖里的 PEP 508 环境标记仍按宿主求值**。在 Windows 上会把 `pywin32`、`pywinpty` 这类 `sys_platform == "win32"` 的包拉进来，同时**静默漏掉** `sys_platform == "linux"` 的包 |
| 直接用系统 Python | Hermes 要求 `>=3.11,<3.14`；信创机常见 3.8/3.9，pip 第一关就拒绝，而且系统 Python 不能动 |
| `python -m venv` + 系统 pip | 系统环境可能没有 pip 或过旧 |
| 把 venv 整个拷到目标机 | venv 里有绝对路径和平台相关二进制，跨机不可用 |
| `pip install .`（源码） | 上游 `setup.py` **明确禁止**在 Nix 之外构建 wheel/sdist |

## 3. 核心设计

### 3.1 构建位置：arm64 runner + manylinux 容器，两层缺一不可

```
GitHub Actions (ubuntu-24.04-arm)          glibc 2.39  ← 只提供架构
    └── docker run quay.io/pypa/manylinux_2_28_aarch64   glibc 2.28  ← 提供 glibc 基线
            └── build_bundle.py --native
```

**这是本项目最贵的一个坑。** 只满足"arm64 runner"会产出一个
构建日志全绿、拷到信创机却 `GLIBC_2.39 not found` 的包，因为编译出来的
原生扩展链接到了 runner 的 glibc。

`build_bundle.py` 里有两道守卫防这个：

- `preflight_native()`：架构必须是 aarch64、宿主必须是 Linux、
  解释器版本必须和 `--python` 一致；
- `check_host_glibc_not_newer()`：宿主 glibc 不能高于目标基线。

两道都在**动手之前**跑，失败就退出，不产出半成品。

### 3.2 依赖闭包：从 `uv.lock` 导出，不重新求解

`uv.lock` 里每个 `[[package]]` 都带 `wheels = [{url, hash, size}]`，
覆盖**所有平台**。这比任何二次求解都可靠。

```bash
uv export --frozen --no-emit-project --extra all \
    --format requirements-txt --no-hashes --output-file requirements.universal.txt
```

`--frozen` 表示不动锁文件；`--extra all` 对应上游 `uv sync --extra all --locked`
的那套 curated 集合。然后在**原生 arm64** 上按 marker 求值，
收敛成目标机真正要装的那一份。

### 3.3 wheel 获取：文件名清点，不看报错文本

```
loop:
  pip download --no-deps -r lock --only-binary=:all: -d wheels/
  missing = {锁文件里的 (归一化名, 版本)} - {wheels/ 与 prebuilt/ 里已有的 wheel}
  if not missing: break
  for spec in missing:
      先单独 pip download <name>==<ver>        # 多数"缺失"只是被同批失败者带崩
      确实下不到 → pip wheel <name>==<ver> -w prebuilt/   # sdist-only，本地构建
```

两个关键点：

- **判定依据是"文件名清点"**，不是解析 pip 的报错。依赖图较深时 pip 只给
  笼统的 `ResolutionImpossible`，**不逐包点名**是哪个没有 wheel，
  形如 `No matching distribution found for X` 的正则会全部落空。
- `pip download -r lock` 遇到第一个缺 wheel 的包就**整批中止**，
  所以"缺失"多半是没下完。必须先逐个单包重试，最后剩下的才是真的 sdist-only。

### 3.4 为什么用 editable 安装而不是装 wheel

上游 `setup.py` 覆写了 `bdist_wheel` 和 `sdist`，在 `HERMES_NIX_BUILD != 1`
时**直接抛错**（它认为 wheel 会缺 locales/skills/web_dist 等运行时资产）。

但 editable 安装走的是 `build_editable`，**不经过 `bdist_wheel`**，
所以不受该守卫影响。上游 `install.sh` 也是这么做的：

```bash
pip install --no-index -r requirements.lock.txt --no-build-isolation
cd $INSTALL_DIR && pip install --no-index -e . --no-deps --no-build-isolation
```

`--no-build-isolation` 让 pip 用 venv 里已有的 setuptools 构建，
不再去联网取构建后端 —— 所以 `requirements.lock.txt` 里显式补了
`setuptools==83.0.0` 和 `wheel`（版本与 `pyproject.toml` 的
`[build-system].requires` 一致）。

### 3.5 node_modules 必须预构建

`package.json` 的 `allowScripts` 里 `node-pty` 是开启的，而
`node-pty` **没有 Linux 预编译包**，每次安装都落到 `node-gyp rebuild`。
信创机通常没有 `make`/`g++`，这一步必挂。

所以在 arm64 容器里先装好（容器自带 gcc/g++/make），打包成 tarball，
目标机只是解压。

只装需要的 workspace（默认含桌面版）：

```bash
npm ci --workspace ui-tui --workspace web --workspace apps/desktop \
       --workspace apps/shared --include-workspace-root
```

`ui-tui` / `web` 是 CLI 的 TUI 与 dashboard 前端，始终装。
`apps/desktop` + `apps/shared` 只在 `with_desktop`（默认开）时装 ——
拉进来会连带 `electron`（postinstall 下载 linux-arm64 二进制）和
`electron-builder`，不需要桌面版时（`--skip-desktop`）不必付这份体积。
上游 `install.sh` 的 `node_deps_workspace_args()` 是"只装 CLI"的口径，
本方案因为要预打包桌面版而多装两个 workspace。

⚠️ **不要在 workspace 子目录里补装**：`npm ci --workspace X` 里 npm 会把
冲突版本自动落到 `X/node_modules`；但在 `ui-tui/` 里裸跑 `npm ci` 会让
npm 按「只含该子树」的理想树 reify，把根 `node_modules` 里其余 workspace
的依赖当场删掉（详见 3.6 与 `docs/故障排查.md` A10b）。

### 3.6 dashboard 前端必须预构建

`hermes dashboard` 是 FastAPI 后端 + React/Vite SPA，默认
`127.0.0.1:9119`。上游的启动路径是：

```
找 hermes_cli/web_dist
  ├─ 有 → 直接服务（前提：build stamp 也匹配）
  └─ 无 → _do_build_web_ui()
             ├─ npm install --prefer-offline
             └─ npm run build
                  失败 → _report_web_build_failure(..., fatal=True) → sys.exit(1)
```

零网络机器上 `npm install` 取不到 registry，**这条路必挂**。症状很有迷惑性：
命令行 `hermes` 一切正常、`hermes doctor` 也不报错，只有 `hermes dashboard`
在 `→ Building web UI...` 之后挂掉。

所以在构建机预编译（`build_web_ui()`，排在 `pack_repo()` **之前**）：

```bash
npm run build --workspace web      # vite outDir = ../hermes_cli/web_dist
```

三个必须踩准的点：

1. **产物目录**：`vite.config.ts` 写死 `outDir: "../hermes_cli/web_dist"`，
   而上游 `_web_dist_dir()` 也只认这个位置。安装是 editable 的
   （`pip install -e .`），所以 `PROJECT_ROOT/hermes_cli/web_dist` 就是
   源码树里那个目录，随 `repo/hermes-agent-src.tar.gz` 一起入包
   （`web_dist` 不在 `REPO_EXCLUDES` 里）。

2. **必须用 `--workspace web` 从仓库根调用**。npm workspace 会把 `web` 的依赖
   **hoist 到根 `node_modules`**，`web/node_modules/` 里只留版本冲突而嵌套的
   少量包（几十 KB 量级）。切到 `web/` 目录里跑会找不到 `vite`/`tsc`。

   ⚠️ 反向同样成立：**绝不能**在 workspace 子目录（`ui-tui/`）里再补一次
   `npm ci` / `npm install`。`ui-tui` 没有自己的 lock，npm 会向上找到工作区根的
   那份 lock 并按「只含该子树」reify —— 副作用是把根 `node_modules` 里其余
   workspace 的依赖**当场删掉**，而 `npm ci` 依旧 exit 0、日志毫无痕迹。
   构建器里删掉了那次安装并加了 `assert_web_toolchain()` 兜底，
   详见 `fetch_node_modules()` 的注释与 `docs/故障排查.md` A10b。

3. **光有 dist 不够，还要写 build stamp**。上游 `_web_ui_build_needed()`
   的判据是「dist 里有 `index.html` 或 `.vite/manifest.json`」**且**
   「`$HERMES_HOME/web-ui-build-stamp.json` 的内容哈希 == 当前源码树哈希」。
   戳在 `HERMES_HOME` 里、**不在仓库里**，所以只能由 `install.sh`
   在目标机上用 venv 的 Python 调上游
   `_compute_web_ui_content_hash()` 现算一次。漏了这一步，裸跑
   `hermes dashboard` 仍会判"需要重建"→ 又回到 npm 那条死路。

兜底路径：`hermes dashboard --skip-build`（或设 `HERMES_WEB_DIST`）
只校验 `index.html` 存在，**完全不碰 npm**。

### 3.7 Hermes Desktop（Electron 壳）必须预打包

`apps/desktop/` 是 **Electron 40 + React 19** 的原生壳，命令 `hermes desktop`
（别名 `hermes gui`）。上游的启动路径比 dashboard 更重：

```
_desktop_build_needed(..., source_mode=False)
  ├─ 否 → 直接启 release/linux-*-unpacked/<exe>
  └─ 是 → npm ci
            └─ electron-builder → @electron/get 下载 Electron 运行时
                                   （~110 MiB zip / ~290 MiB 解包）
                  失败 → 窗口起不来
```

离线机上这三步一步都走不通，所以在构建机打包成 unpacked 树：

```bash
node scripts/rebuild-native.mjs arm64        # node-pty → Electron ABI
npm run pack                                 # = build + builder --dir --publish never
tar -czf hermes-desktop-linux-arm64.tar.gz -C release linux-arm64-unpacked
```

五个必须踩准的点：

1. **只能用 `npm run pack`**（= `builder --dir --publish never`），
   不能用 `dist:linux`，也不要自己拼 `--linux --arm64`。
   AppImage / deb / rpm 三个 target 都要调 `fpm`，而 electron-builder
   分发的 fpm **只有 x86_64** —— 在 arm64 构建机上必然失败。`--dir`
   只产出 unpacked 目录，完全绕开这条路，目标机运行期也不需要打包工具。
   另外 `run-electron-builder.mjs` 已经替你 pin 了 `--publish never` ——
   CI 里 `CI=1` 时 electron-builder 会隐式解析 publish 目标并读
   `<projectDir>/.git/config`，在 `apps/desktop`（自己没有 `.git`）下会报
   `Cannot detect repository by .git/config`。

2. **`node-pty` 必须重编到 Electron ABI**。npm ci 编出来的是 **Node ABI**
   （Node 24 = 137），Electron 40 加载原生模块要 **Electron ABI**（143）。
   不匹配时内嵌终端报 `NODE_MODULE_VERSION` mismatch 后整块不可用。
   用上游自带的 `apps/desktop/scripts/rebuild-native.mjs`
   （内部是 `@electron/rebuild`，`onlyModules: ['node-pty']`）。
   ⚠️ 这一步会改写根 `node_modules/node-pty`，所以必须在
   `fetch_node_modules()` **之后**跑 —— 给 CLI 用的那份 tarball 到那时
   已经打好了，否则 CLI 会拿到 Electron ABI 的 `.node` 而加载失败。

3. **产物不进源码快照**。unpacked 树实测 **343.9 MiB**（Electron 运行时的
   `dist` 是大头），混进 `pack_repo()` 会让源码包翻几倍。所以
   `apps/desktop/release` 加进 `REPO_EXCLUDES`，产物**单独**打成
   `bundle/desktop/*.tar.gz`（实测 135.1 MiB）。漏排的症状与 node_modules
   那条一样："包莫名大了几百 MB，日志全绿"。

4. **光有产物不够，还要写 build stamp**。上游
   `_desktop_build_needed()` 的判据是「`release/` 里有可执行文件」**且**
   「`resources/app.asar.unpacked/dist/index.html` 在（torn 检查）」**且**
   「`$HERMES_HOME/desktop-build-stamp.json` 的 `sourceMode=false` 且内容
   哈希 == 当前源码树哈希」。戳不在仓库里，只能由 `install.sh` 在目标机上
   用 venv 的 Python 调上游 `_compute_desktop_content_hash()` 现算。
   **`sourceMode` 必须写 `false`** —— `_stamp_is_current()` 会比对它，
   写成 `true` 等于没写，裸跑仍会去 npm 构建。
   另注意 `app.asar.unpacked/dist/index.html` 必须在场：缺了它
   `--skip-build` 起来是个**白窗口**，比启动失败难查得多。

5. **桌面版的"构建工具链"必须挡在包外**。
   `npm ci --workspace apps/desktop` 会把 `electron` / `electron-builder` /
   `app-builder-bin` 等一大批装进（hoist 到）根 `node_modules`，而根
   `node_modules` 是整体打成 `node_modules.tar.gz` 送给目标机的 ——
   可目标机跑的是 `desktop/` 里那棵**自包含**的 unpacked 树（主进程被 esbuild
   打进 `app.asar`，原生模块在 `app.asar.unpacked`），**完全不碰 repo 的
   `node_modules`**。实测代价（2026-09-17，同分支前后对比）：

   | 项 | 无桌面版 | 有桌面版 | Δ |
   |---|---|---|---|
   | `node_modules/node_modules.tar.gz` | 98.9 MB | 234.9 MB | **+136 MB** |
   | `node_modules/apps__desktop__node_modules.tar.gz` | — | 3.4 MB | +3.4 MB |
   | `desktop/hermes-desktop-linux-arm64.tar.gz` | — | 135.1 MiB | +135.1 MiB |
   | 整包 tar.gz | 697M | 980M | +283 MB |

   真正必要的只有 135.1 MiB（桌面版本体）；那 +136 MB 里运行期只需要 ~1 MB。
   所以 `_nm_tarball_filter()` 在打 tarball 时按路径段排掉
   `TARGET_NM_EXCLUDES` 那批包。三条约束：

   - **只过滤 tar 成员，不删盘上文件** —— electron-builder 打包时正需要
     `node_modules/electron/dist`（`run-electron-builder.mjs` 会传
     `-c.electronDist=<abs>` 复用它），删了盘上副本就会退化成走
     `@electron/get` 联网下载。
   - **必须识别任意层级的 `node_modules`** —— npm 因版本冲突会把包嵌到
     `node_modules/a/node_modules/b`，只认顶层会漏一大批。
   - **排除表不得与运行期清单相交** —— `react` / `react-dom` / `vite` /
     `typescript` 这些在依赖树里与构建工具共享，排错一个就是运行期炸。
     `test_desktop.py` 有这条反向断言，并禁止过滤器里出现
     `shutil.rmtree` / `os.remove` / `unlink`。

   另：`app-builder-bin` 这类包夹带着 mac/win 各平台二进制，留着也等于把
   "只发 aarch64"这条不变量破在包里（CI 的 wheel 检查只看 `.whl`，查不出它）。

兜底路径：`hermes desktop --skip-build` 直接启动产物，完全不碰 npm。

**运行前提**：需要一个图形会话（X11/Wayland）和 GTK3/NSS/GBM/atspi 一整套
系统库（Electron 自带 Chromium，但这些库要宿主提供，且多为启动时 dlopen，
`ldd` 查不出来）。`check-env.sh` 会查 `ldconfig` 缓存并逐个列出缺哪个。
root 身份启动时 Electron 的 setuid sandbox（`chrome-sandbox` 需 `root:4755`）
不满足会拒绝启动，上游 `_packaged_desktop_launch_command()` 会自动补
`--no-sandbox` 兜底。

`build/test_desktop.py`（80 项断言）把上面每一条连同调用顺序
（`fetch_node_modules` → `build_desktop` → `pack_repo`）、`REPO_EXCLUDES`
里的 `apps/desktop/release` 一起钉死。

### 3.8 Playwright Chromium

Chrome 官方**不发 Linux arm64 二进制**，但 Playwright 自己维护
`chromium-linux-arm64` 构建。所以在 arm64 上 `npx playwright install chromium`
是能拿到原生 ARM64 Chromium 的。

关键点：**别让离线机去下载**。构建时设 `PLAYWRIGHT_BROWSERS_PATH`
指向暂存目录，把整个目录打包；安装时铺到
`$HERMES_HOME/ms-playwright`，并在 `hermes` 入口里导出同名环境变量，
Playwright 就认这个路径、不会触发下载。

### 3.9 中文分词的原生扩展

`native/fts5_cjk` 是个 C 扩展（`cjk_unicode61` FTS5 tokenizer），
不编的话 1-2 字的中文/韩文/日文检索会退化成 LIKE 全表扫。

它在 manylinux 容器里编译（自带 gcc），产物 `.so` 铺到
`$HERMES_HOME/lib/`。这是**用容器构建的另一个理由**：
如果只在 runner 本体上编，这个 `.so` 会带上 glibc 2.39 的符号需求。

## 4. 目标机安装流程

```
check-env.sh（只读预检）
    ↓
install.sh
    0. 环境预检（架构 / glibc / 磁盘 / 图形会话）
    1. 校验 MANIFEST.sha256
    2. 解压 CPython 3.11 独立运行时 → $INSTALL_DIR/runtime/python
    3. 解压源码 → $INSTALL_DIR
    4. $PY -m venv venv
       pip install --no-index -r requirements.lock.txt --no-build-isolation
       pip install --no-index -e . --no-deps --no-build-isolation
       关键依赖 import 冒烟测试
    5. 解压 Node.js → $HERMES_HOME/node，链接 node/npm/npx 到 bin 目录
    6. 解压预构建 node_modules → 对应 workspace 目录
    7. 解压 Chromium → $HERMES_HOME/ms-playwright，ldd 检查缺哪些系统库
    8. 铺 rg/ffmpeg/uv → $HERMES_HOME/bin，fts5_cjk.so → $HERMES_HOME/lib
    9. 前端产物已在源码树里 → 补写 web-ui-build-stamp.json
   10. 解压桌面版 → apps/desktop/release，补写 desktop-build-stamp.json
       （chrome-sandbox setuid / 图形库体检 / 图形会话提示）
   11. 初始化 $HERMES_HOME 目录结构 + 首装时生成 config.yaml / .env
   12. 生成 hermes / hermes-agent / hermes-acp 入口
```

### 入口脚本里为什么要写死这几个环境变量

```bash
unset PYTHONPATH; unset PYTHONHOME
export HERMES_HOME=...
export PLAYWRIGHT_BROWSERS_PATH=...
export PATH="$HERMES_HOME/bin:$HERMES_HOME/node/bin:$PATH"
```

- `PYTHONPATH`/`PYTHONHOME`：上游也这么做。继承来的值会让 Python 从
  **另一个 checkout** 导入模块，表现为"刚装好却是旧代码"。
- `PLAYWRIGHT_BROWSERS_PATH`：指向包内铺好的浏览器缓存，避免 Playwright
  认为没装而尝试下载。
- `PATH`：让 `rg`/`ffmpeg`/`uv`/`node` 能被 Hermes 内部的
  `command -v` 探测到。

## 6. 不变量与验收

构建前（CI 前置门，秒级）：

- `check_undefined.py`：AST 未定义名。拦"语法合法但调用了不存在的函数"。
- `test_native_mode.py`：19 项断言，锁死 pip 调用参数不含
  `--platform`/`--python-version`/`--abi`/`--implementation`；
  并验证 `--native` 在各种错误宿主上确实会被拒绝。
- `test_web_ui.py`：39 项断言，锁死"前端必须预编译进包"这条链 ——
  其中最关键的是 **`build_web_ui()` 必须排在 `pack_repo()` 之前**
  （排在后面 = 产物进不了源码快照 = 白编），以及 `install.sh`
  确实补写了 build stamp。
- `test_desktop.py`：80 项断言，锁死"Hermes Desktop 必须预打包进包"这条链 ——
  打包方式必须是 `npm run pack`（不能碰 fpm）、`node-pty` 必须在 pack 前
  重编到 Electron ABI、`build_desktop()` 必须夹在 `fetch_node_modules()`
  与 `pack_repo()` 之间、`apps/desktop/release` 必须在 `REPO_EXCLUDES` 里、
  `install.sh` 的 build stamp 里 `sourceMode` 必须为 `false`、
  构建期专用包必须在 `TARGET_NM_EXCLUDES` 里且与运行期清单不相交。
- `test_workflow.py`：工作流自检 —— YAML 可解析、`runs-on` 架构、
  manylinux 容器、`timeout-minutes`、`permissions`、每个 `run` 块的
  `bash -n`、`github.event.inputs.*` 引用完整性，以及 `set -o pipefail`
  下末段提前退出的管道（`| head`、`| grep -q`）—— 后者会把整条管道判失败，
  或在 `if !` 里把条件**静默反转**。
- `test_push_api.py`：`push_api.py` 的 blob 批量解析逐字节自测
  （重算 `sha1("blob <len>\0" + content)` 与 git index 比对）。
- `test_download.py`：下载器自测，本地起一个支持 Range 的 HTTP 服务，
  验证多分片并发、残缺续传、小文件退化为单连接，以及临时分片清理。

构建中：

- `audit_wheels()`：所有 wheel 平台标签必须是 `aarch64` 或 `any`；
  禁止混入 sdist；`manylinux_2_<n>_aarch64` 的 n 不得超过基线。
- `build_web_ui()`：产物必须落在 `hermes_cli/web_dist` 且含
  `index.html` + js/css 资源，否则直接失败（不静默产出半成品包）。
- `build_desktop()`：`npm run pack` 之后必须能在
  `release/linux-arm64-unpacked/{hermes,Hermes}` 找到可执行文件，
  且 `resources/app.asar` 与 `resources/app.asar.unpacked/dist/index.html`
  都在场 —— 后者缺了 `--skip-build` 起来就是个白窗口。

构建后（CI 步骤）：

- `tar -tzf` 结构抽检，关键条目逐个存在性断言；
- 钻进嵌套的 `repo/hermes-agent-src.tar.gz`，断言
  `hermes_cli/web_dist/index.html` 在场且 `web_dist/assets` 下有 js/css；
- 再钻进 `desktop/hermes-desktop-linux-arm64.tar.gz`，断言 unpacked
  可执行文件、renderer 产物与 `.node` 原生模块都在场；
- 断言源码快照里**没有** `node_modules/` 与 `apps/desktop/release/`
  这两份重复副本；
- 输出 sha256 到 job summary。

目标机：

- `check-env.sh` 的 glibc / 磁盘 / 包完整性 / dashboard 前端 /
  desktop 产物 / Chromium 与桌面版缺库 / 图形会话检查；
- `install.sh` 的依赖 import 冒烟测试 + Web UI 与 Desktop build stamp 写入。

## 7. 本方案不覆盖的部分（及原因）

| 功能 | 上游怎么装 | 为什么不打包 | 影响 |
|---|---|---|---|
| **Browser Use CLI** | `uv tool install browser-use` | 是一整套独立依赖树（含自己的 playwright），体积大、与内置浏览器工具重复 | Hermes 回退到内置浏览器工具 + 包内 Chromium，功能可用 |
| **cua-driver（Computer Use）** | `curl ... /cua-driver/install.sh \| bash` | 上游是 curl 管道脚本，离线无法执行；且它主要面向 macOS 桌面控制 | `computer_use` toolset 不可用 |
| **lazy-install 类后端** | 首次使用时 `pip install` | 离线必然失败 | 用到的后端要在构建时的 `[all]` 里 |
| **本地模型 / 推理** | — | 与 Hermes 无关 | 需另行搬运 |

想扩展覆盖范围时，改 `build_bundle.py` 里对应的 `fetch_*` 步骤，
并在 CI 的 `--extra` 参数上放开相应 extra。

**Hermes Desktop 是打包进来的，但它有宿主侧前提**：图形会话 +
GTK3/NSS/GBM/atspi 等系统库（Electron 自带 Chromium，但这些库要宿主提供，
且多为启动时 `dlopen`，`ldd` 查不出来）。这两项都不是"打包能解决"的问题，
所以 `check-env.sh` 把它们做成警告项列出，缺了也只降级 —— 核心 CLI 与
`hermes dashboard` 不受影响。无图形会话的机器建议构建时 `--skip-desktop`，
包会小 ~140 MiB。

## 8. 一句话总结取舍

> **能在 arm64 Linux 上构建的，就不要试图模拟它。**
>
> 原生模式的全部价值在于：平台本来就是对的。一旦接受了这个前提，
> `--platform`、marker 劫持、`--no-build-isolation` 强塞、sdist 降级
> 这一整类交叉构建的复杂度就**不是被绕过了，而是压根不存在**。
> 余下的所有工作，都只是"把东西提前拿下来放进包里"。
