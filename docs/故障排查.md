# 故障排查

按"症状 → 原因 → 处置"编排。前半段是**构建期**（CI / 构建机），
后半段是**目标机**。

---

## A. 构建期

### A1. `--native 要求 aarch64 宿主` / `--native 要求 Linux 宿主`

**原因**：在 x86 机器或 macOS/Windows 上跑原生模式。

**处置**：原生模式必须在 ARM64 Linux 上跑。用 GitHub Actions：

```yaml
runs-on: ubuntu-24.04-arm
```

然后 `docker run quay.io/pypa/manylinux_2_28_aarch64`。

---

### A2. `宿主 glibc 2.39 高于目标基线 2.28`

**原因**：把构建放在了 runner 本体的 shell 里，而不是容器里。

**处置**：整条构建命令必须包在 `docker run ... manylinux_2_28_aarch64` 里。
**runner 提供架构，容器提供 glibc 基线** —— 少一层就会产出
"构建全绿、拷过去 GLIBC not found" 的包。

---

### A3. `仍有 N 个 pin 拿不到 wheel`

**原因**：这些包在 PyPI 上**只有 sdist、没有任何 wheel**。

**排查**（几秒钟定性，区分"真缺失"和"其实有 wheel 只是批量下载被带崩"）：

```bash
# 看日志里"逐个单包重试"之后还剩几个
grep -A5 '确实只有 sdist 的包' dist/logs/build.log
```

**处置**：

- 如果只剩零星几个 → 构建器会自动 `pip wheel` 本地构建成 wheel，
  产物进 `wheels-prebuilt/`。若构建失败，看日志尾部的编译报错
  （通常是缺 `-devel` 包，容器里 `dnf install -y <pkg>-devel`）。
- 如果是**一大批** → 说明批量下载在中途死了却没被识别。检查
  `requirements.lock.txt` 是否完整、PyPI 镜像是否可用。
- 想快速判定"是真冲突还是缺 wheel"：

```bash
uv pip compile req.in --python-version 3.11 --python-platform aarch64-manylinux_2_28 --index-url <mirror>
uv pip compile req.in --python-version 3.11 --python-platform aarch64-manylinux_2_28 --index-url <mirror> --only-binary :all:
# 前者成功、后者失败 ⇒ 就是"缺 wheel"，不是版本冲突
```

---

### A4. `wheel 目录混入 sdist` / `平台标签有问题`

**原因**：

- 混入 sdist → 离线安装阶段要编译，而目标机没有编译器。
- 平台标签错 → 下载阶段误用了交叉参数，或宿主架构不对。

**处置**：看 `audit_wheels()` 打出的具体文件名。若出现
`manylinux_2_34_aarch64 ... 需要 glibc 2.34 > 基线 2.28`，
说明容器不是 manylinux_2_28，或者目标机基线设高了/低了。

---

### A5. `npm ci` / `npm install` 失败

**常见原因**：

| 报错特征 | 原因 | 处置 |
|---|---|---|
| `ETARGET` / `min-release-age` | npm 落在 11.10.0–11.16.x 坏区间（该区间忽略了 `min-release-age-exclude`） | 换 Node 线。`build_bundle.py` 的 `npm_ok()` 已经会避开，除非手动指定了 node_line |
| `node-gyp rebuild` 失败 | 容器缺 `make`/`g++` | `ci-entry.sh` 已装；确认没被改动 |
| `ENOENT ... package-lock.json` | `npm ci` 需要 lock，而检出里没有 | 构建器会自动回退 `npm install` |

### A6. `没找到 node-pty 的原生 .node 产物`

**原因**：node-pty 编译失败，或 `npm` 装的是别的平台版本。

**处置**：

```bash
# 在容器里手动确认
ls -la /work/.ci/hermes-agent/node_modules/node-pty/build/Release/
```

有 `.node` 文件就正常。没有的话看 `npm` 那一段日志；
PTY 功能会受影响，但核心 CLI 仍可用。

---

### A7. GitHub 相关下载失败 / 超时

**原因**：境内网络对 `github.com` 的部分 A 记录会 TCP 超时
（`api.github.com` 通常还行）。

**处置**：

- CI 里不需要加速（runner 就在 GitHub 网络内）。
- 本机构建加 `--gh-mirror`，会依次尝试
  `ghfast.top` / `gh-proxy.com` / `ghproxy.net`。
- 或者手动把对应文件放进期望路径，构建器检测到就跳过下载
  （下载函数是幂等的，已有且校验通过就不重复下）。

---

### A8. `gh run download` 卡住不动

**原因**：`gh run download` / `gh api` **没有超时**，链路一抖就无限挂起。

**处置**：别用它。用仓库自带的 `build/gh_run.py`：

```bash
python build/gh_run.py watch    --repo <owner>/<repo> --run <RUN_ID>
python build/gh_run.py arts     --repo <owner>/<repo> --run <RUN_ID>
python build/gh_run.py download --repo <owner>/<repo> \
       --artifact <ART_ID> --out dist --parts 6
python build/gh_run.py verify   --tarball dist/hermes-offline-arm64.tar.gz
```

它给每次读操作设 socket 超时、按 `Range` **多分片并发**拉、每片独立断点续传、
下载完用 API 的 `artifact.digest`（`sha256:...`）做完整性校验 ——
字节数一致也可能是凑巧。`verify` 再补一层包内体检：关键条目是否齐全、
有没有混进非 aarch64 的 wheel、有没有 glibc 基线高于目标机的 wheel。

> **为什么要分片**：跨境链路上单条 TCP 连接的吞吐常被压在几百 KiB/s。
> 实测同一个 692 MiB 的 artifact：单连接 ~200 KiB/s（要跑 50 分钟以上），
> `--parts 6` 之后聚合 ~4.8 MiB/s（约 2 分钟）—— 瓶颈从"单连接"变成了"总带宽"。
> 默认 4 片；每片至少 4 MiB，太小的文件会自动退回单连接。

### A9. `git push` 静默失败 / 长时间挂起

**症状**：`git push` 既不报错也不推进，卡很久后超时；同一台机器上 `gh`
和 `api.github.com` 却一切正常。

**原因**：境内网络对 `github.com` 的部分 A 记录 TCP 超时，而 git 走的是它的
smart-HTTP 端点。`api.github.com` 属于另一组域名，通常可达 —— 于是出现
"网页能开、`gh` 能用、偏偏 `git push` 推不上去"的分裂现象。

**处置**：绕开 git 的 smart-HTTP，直接用 Git Data API 推送：

```bash
git -C . commit ...            # 脚本读的是 index，不是工作区，必须先提交
python build/push_api.py . <owner>/<repo>
```

脚本依次打 `GET /git/ref`（取父节点，保持历史连续）→ `POST /git/trees`
（内联 content，一次建完）→ `POST /git/commits` → `PATCH /git/refs`。
推完会回读校验：**远端根 tree 的 sha 必须与本地 `HEAD^{tree}` 相等**，
相等即整棵目录树逐字节相同。

> 这条判据是刻意选成"整树 sha"而不是"逐文件比对"的。`git ls-files -s`
> 会按 `core.quotePath` 把非 ASCII 路径 quoting 成 `"docs/\346\225..."`，
> 把它当路径交给 trees API，GitHub 会老老实实建出一个名叫 `"docs` 的目录 ——
> 内容全对、目录结构全错，而逐文件比对**会全绿**（两侧拿到同一个错误串）。
> 只有根 tree sha 能一眼指出"多了一个 `"docs`、少了 `docs`"。

### A10. Web UI 预编译失败（`[7/12] 预编译 Web UI`）

**症状**：构建跑到 `npm run build --workspace web` 失败，或报
`预编译跑完了，但 hermes_cli/web_dist/index.html 不存在`。

**原因分四种**：

1. **真的编不过** —— TS 类型错误、依赖没装全。看构建日志里 vite/tsc 的
   报错尾巴，和本地 `cd web && npm run build` 是同一份输出。
2. **依赖被静默删掉了**（最阴的一种，见下面专条）—— 症状是 `tsc` 甩出几百条
   `TS2307: Cannot find module 'react-dom' / 'lucide-react' / '@nous-research/ui'`。
3. **`web/node_modules` 与 `--workspace web`** —— npm workspace 会把 `web` 的
   依赖 **hoist 到根 `node_modules`**，所以正常的 `web/node_modules/` 只留版本
   冲突而嵌套的少量包（实测 `@babel` / `@rolldown` / `semver` / `lru-cache`）。
   `vite` / `tsc` 都在根 `node_modules/.bin/` 里，所以构建必须用
   `--workspace web` 从**仓库根**调用；切到 `web/` 里直接跑会找不到工具链。
4. **上游改了 vite 的 `outDir`** —— 报错里会附带
   `（在 web/dist 发现了产物，说明上游改了 vite outDir）`。
   上游 `_web_dist_dir()` 硬认 `hermes_cli/web_dist`，改了就得同步
   `build_web_ui()` 里的路径，否则会产出一个"编了但运行时找不到"的包。

#### A10b. 依赖树被一次多余的 `npm ci` 剪掉（真实踩坑，2026-09-17）

**判据**：包里的 `node_modules/web__node_modules.tar.gz` **只有几百字节、解开来
是空目录**。以前这条被当成"hoist 的正常现象"，其实它是依赖被删的证据。

**成因**：在 workspace 子目录（`ui-tui/`）里跑 `npm ci` / `npm install`。
`ui-tui` 自己没有 `package-lock.json`，npm 会**沿目录树向上**找到工作区根的那份
lock，然后按「只含 ui-tui 这棵子树」的理想树 reify —— reify 的副作用是把根
`node_modules` 里所有**不属于** ui-tui 的包**当场删掉**，包括 web 要用的
`react-dom` / `react-router` / `lucide-react` / `@nous-research/ui`。
实测：这一步之后根 `node_modules` 顶层只剩一个 `ui-tui` 符号链接。

**为什么难查**：`npm ci` 全程 **exit 0**，日志里没有任何痕迹；
而 `tsc` 本身**照样能跑** —— 因为 `ui-tui` 的 `devDependencies` 里也有
`typescript`，剪枝后活了下来。于是故障伪装成"只有 web 的包丢了"。

**现在的防线**：
- `fetch_node_modules()` 里删掉了那次安装，并用注释钉死不许加回来；
- 装完立刻跑 `assert_web_toolchain()`，缺包在**安装步骤**就报错，
  不会再拖到 `tsc` 甩几百行 TS2307；
- `build/test_web_ui.py` 里有反向断言（`cwd=repo / "ui-tui"` 不得出现）。

**不要用 `--skip-web-ui` 糊过去** —— 那个开关只为本地快速迭代存在。
离线目标机没有 npm registry，包一旦缺前端，`hermes dashboard` 必失败。

**为什么这条不能只在目标机兜底**：`check-env.sh` 和 CI 的「校验产物」
都会断言 `hermes_cli/web_dist/index.html` 在包内。缺了它，CI 直接红。

### A11. Hermes Desktop 打包失败（`[8/12] 打包 Electron 桌面版`）

**症状**：`npm run pack` 失败，或报
`打包跑完了，但 release 里没有 unpacked 可执行文件`。

**原因分五种**：

1. **误用了 `dist:linux` 而不是 `pack`** —— 报错里会出现 `fpm` 或
   `cannot execute binary file`。AppImage/deb/rpm 三个 target 都要调 `fpm`，
   而 electron-builder 分发的 fpm **只有 x86_64**，在 arm64 构建机上必挂。
   构建器用的是 `npm run pack`（= `builder --dir`），只产出 unpacked 目录。
   **不要**把它改回 `dist:linux`。
2. **electron / electron-builder 没装上** —— `apps/desktop` 的依赖被 hoist
   到根 `node_modules`，`fetch_node_modules()` 的 workspace 列表必须包含
   `apps/desktop` 与 `apps/shared`。装完 `assert_desktop_toolchain()`
   会点名缺哪个包。
3. **Electron 运行时下载失败** —— `electron` 包的 postinstall 会经
   `@electron/get` 去 GitHub 拉 linux-arm64 二进制。国内直连不稳时设
   `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`（实测该镜像
   偶发 SSL `UNEXPECTED_EOF`，此时回退 GitHub releases 直连）。
4. **输出目录名变了** —— electron-builder 换了目录名的话，
   同步 `DESKTOP_UNPACKED_DIRS`（当前认 `linux-arm64-unpacked` /
   `linux-unpacked`）。报错里会把 `release/*-unpacked/` 下实际看到的东西
   列出来。
5. **renderer 产物缺失** —— 报
   `unpacked 树里没有 renderer 产物：.../app.asar.unpacked/dist/index.html`。
   说明 electron-builder 的 `asarUnpack` 没把 `dist/**` 解出来。
   这个必须当场拦下：缺了它 `--skip-build` 启动出来是个**白窗口**，
   比启动失败更难判断。

**为什么不能只在目标机兜底**：`check-env.sh` 和 CI 的「校验产物」都会钻进
`desktop/hermes-desktop-linux-arm64.tar.gz` 断言 unpacked 可执行文件、
renderer 产物与 `.node` 原生模块都在场。缺了 CI 直接红。

**不要用 `--skip-desktop` 糊过去** —— 除非目标机确实没有图形会话。

## B. 目标机

### B1. `GLIBC_2.39 not found` / `version 'GLIBC_2.34' not found`

**原因**：包是在高于目标基线的 glibc 上构建的，或目标机 glibc 低于基线。

**处置**：

```bash
getconf GNU_LIBC_VERSION        # 目标机实际 glibc
cat build-info.json             # 包的基线
```

两者对齐后重打。`--glibc 2.17` 可适配更老的系统（部分依赖要 pin 老版本）。

---

### B2. `install.sh` 里"关键依赖 import 失败"

**症状**：`installing` 阶段末尾打印

```
以下原生/关键依赖导入失败：
  - cryptography: ImportError: libssl.so.1.1: cannot open shared object file
```

**原因**：不是 Python 层的问题，是缺**系统共享库**。

**处置**：按缺失的 `.so` 名字装对应系统包。常见对应关系：

| 缺失 | CentOS/openEuler/Kylin | Debian/UOS |
|---|---|---|
| `libssl.so.1.1` / `libcrypto.so.1.1` | `openssl-libs` | `libssl1.1`（或 `libssl3`） |
| `libffi.so.*` | `libffi` | `libffi7`/`libffi8` |
| `libz.so.*` | `zlib` | `zlib1g` |
| `libgcc_s.so.1` | `libgcc` | `libgcc-s1` |

离线机上如果装不了系统包，就在**构建时**改成静态链接的变体，
或换用不需要该库的依赖版本。

---

### B3. `bad interpreter: /bin/bash^M`

**原因**：脚本被存成了 CRLF 行尾。这个报错**完全不提行尾**，极易误判。

**处置**：项目根有 `.gitattributes`（`*.sh text eol=lf`）来防这个。
若已中招：

```bash
sed -i 's/\r$//' install.sh check-env.sh
```

CI 里 `test_native_mode.py` 有一项断言专门拦 CRLF 的 `.sh`。

---

### B4. Chromium 启动失败 / `error while loading shared libraries`

**原因**：Playwright 的 Chromium 依赖一批系统库，信创机默认多数没有。

**处置**：`check-env.sh` 会 `ldd` 出**具体缺哪几个**，按提示装：

```bash
# CentOS / openEuler / Kylin
sudo yum install -y nss nspr libdrm libxkbcommon mesa-libgbm pango cairo alsa-lib atk at-spi2-core cups-libs
# Debian / UOS
sudo apt install -y libnss3 libnspr4 libdrm2 libxkbcommon0 libgbm1 libpango-1.0-0 libcairo2 libasound2 libatk1.0-0 libatk-bridge2.0-0 libcups2
```

**这只影响浏览器工具**，核心 CLI 不受影响。

---

### B5. `PLAYWRIGHT_BROWSERS_PATH` 相关：明明铺了浏览器却说要下载

**原因**：环境变量没传进子进程。

**处置**：`hermes` 入口脚本里已经 export 了。如果你绕过入口直接调
`venv/bin/python`，需要自己带上：

```bash
export PLAYWRIGHT_BROWSERS_PATH=$HERMES_HOME/ms-playwright
```

---

### B6. 中文检索变慢 / 走全表扫

**原因**：`fts5_cjk.so` 没铺上，或 `sessions.cjk_fts` 被关掉了。

**处置**：

```bash
ls -l $HERMES_HOME/lib/fts5_cjk.so
grep cjk_fts $HERMES_HOME/config.yaml     # 应为 true 或不设
hermes sessions optimize-storage           # 对已有数据库回填索引
```

环境变量 `HERMES_FTS5_CJK_SO` 可以显式指定 `.so` 路径。

---

### B7. `hermes` 命令找不到

**原因**：`/usr/local/bin`（或 `~/.local/bin`）不在 PATH 上。
RHEL 系非登录 shell（`su`、`sudo -s`、tmux）只 source `/etc/bashrc`，
不会带上 `/usr/local/bin`。

**处置**：

```bash
export PATH="/usr/local/bin:$PATH"                    # 当前会话
echo 'export PATH="/usr/local/bin:$PATH"' >> ~/.bashrc  # 永久
```

---

### B8. `hermes update` 报网络错误 / 部分功能首次使用即失败

**这是预期行为，不是 bug。**

离线环境下：

- `hermes update` 拉不到代码 → 升级要重打离线包后重跑 `install.sh --force`；
- lazy-install 类后端（某些 TTS/STT、搜索、消息平台）首次使用时才装的
  组件装不上 → 需要在**构建时**就把对应 extra 包含进 `[all]`。

---

### B9. 想确认包有没有被动过 / 介质有没有坏

```bash
cd hermes-offline-arm64
sha256sum -c MANIFEST.sha256 | grep -v ': OK$'
```

无输出 = 完好。`install.sh` 默认也会先做这一步（`--no-verify` 可跳）。

### B10. `hermes dashboard` 起不来 / 提示 `Building web UI...` 然后 npm 报错

**症状**：命令行 `hermes` 一切正常，但 `hermes dashboard` 打印
`→ Building web UI...`，接着 `npm install` 报错（`ENOTFOUND`、
`network timeout`、`ETIMEDOUT`），最后 `sys.exit(1)`。

**原因**：包里缺预编译前端，上游走了"现场编译"分支：

```
_do_build_web_ui() → npm install --prefer-offline → npm run build
```

零网络机器上 `npm install` 取不到 registry，必然失败。

**先确认是哪种情况**：

```bash
ls /usr/local/lib/hermes-agent/hermes_cli/web_dist/index.html   # 前端在不在
ls /root/.hermes/web-ui-build-stamp.json                        # 戳在不在
```

| web_dist | build stamp | 结论 |
|---|---|---|
| 有 | 有 | 不该触发重建 —— 查 `hermes doctor` 输出，可能是路径不对 |
| 有 | **无** | 只是缺戳，补写即可（见下） |
| **无** | — | 包本身就缺前端，必须重打离线包（构建时别加 `--skip-web-ui`） |

**处置 1（缺戳，最快）**：直接跳过重建，服务包内 dist：

```bash
hermes dashboard --skip-build
```

**处置 2（缺戳，补写）**：用 venv 里的 Python 按当前源码树算一次哈希：

```bash
HERMES_HOME=/root/.hermes /usr/local/lib/hermes-agent/venv/bin/python - <<'PY'
import json, datetime, sys
from pathlib import Path
from hermes_cli.main_web_build import _compute_web_ui_content_hash, _web_ui_stamp_path
root = Path("/usr/local/lib/hermes-agent")
stamp = _web_ui_stamp_path()
stamp.parent.mkdir(parents=True, exist_ok=True)
stamp.write_text(json.dumps({
    "contentHash": _compute_web_ui_content_hash(root, root / "web"),
    "source": "manual",
    "builtAt": datetime.datetime.now(datetime.timezone.utc).isoformat(),
}, indent=2) + "\n", encoding="utf-8")
print("stamp →", stamp)
PY
```

之后裸跑 `hermes dashboard` 就不会再碰 npm。`install.sh` 正常情况下
已经自动做了这一步（第 9 步），所以出现"缺戳"多半是拷贝源码树时丢了东西。

> 注意 `_compute_web_ui_content_hash()` 走的是 **内容哈希**，不是 mtime，
> 所以 rsync/拷贝改了时间戳不影响判定；但**改过 `web/` 下任何源文件**
> 就会让戳失效、重新触发重建 —— 届时在离线机上只能 `--skip-build`。

### B11. `hermes desktop` 起不来

分三类症状，先分类再动手：

**① 打印构建日志后挂掉**（`npm ci` / `ENOTFOUND` / `@electron/get` 下载失败）

包里的 desktop 产物或 build stamp 缺了，上游走了"现场构建"分支
（`npm ci` → electron-builder → 下载 Electron 运行时 ~110 MiB）。零网络下必挂。

```bash
ls /usr/local/lib/hermes-agent/apps/desktop/release/linux-arm64-unpacked/hermes
ls /root/.hermes/desktop-build-stamp.json
```

| release 里的 exe | build stamp | 结论 |
|---|---|---|
| 有 | 有 | 不该触发重建 —— 查 `hermes doctor`，可能是 `sourceMode` 不对 |
| 有 | **无** | 只是缺戳，补写即可（见下） |
| **无** | — | 包本身就缺桌面版，必须重打（构建时别加 `--skip-desktop`） |

最快逃生门：

```bash
hermes desktop --skip-build
```

补写戳（注意 **`sourceMode` 必须是 `false`**，原因见下）：

```bash
HERMES_HOME=/root/.hermes /usr/local/lib/hermes-agent/venv/bin/python - <<'PY'
import json, datetime
from pathlib import Path
from hermes_cli.main_desktop import _compute_desktop_content_hash, _desktop_stamp_path
root = Path("/usr/local/lib/hermes-agent")
stamp = _desktop_stamp_path()
stamp.parent.mkdir(parents=True, exist_ok=True)
stamp.write_text(json.dumps({
    "contentHash": _compute_desktop_content_hash(root),
    "sourceMode": False,          # ← 必须 false：_stamp_is_current() 会比对它
    "source": "manual",
    "builtAt": datetime.datetime.now(datetime.timezone.utc).isoformat(),
}, indent=2) + "\n", encoding="utf-8")
print("stamp →", stamp)
PY
```

> `sourceMode: true` 表示"这是源码模式"，`_stamp_is_current()` 拿它跟当前
> 运行模式比对 —— 打包模式下写 `true` 等于**没写**，仍会去 npm 构建。
> 这是最容易写错、且报错信息完全指不到的一处。

**② 窗口没出来、或出来是白窗口**

- **白窗口** = renderer 产物没进包。`app.asar.unpacked/dist/index.html`
  必须在；`check-env.sh` 与 CI 都会断言它。
- **完全没窗口** = 看终端有没有 `NODE_MODULE_VERSION 137 vs 143` ——
  那是 `node-pty` 还是 Node ABI，说明构建机漏了 `rebuild-native.mjs`
  （只影响内嵌终端，主界面仍应可用）。

**③ 直接报错退出（库缺失 / sandbox）**

```bash
# 看缺哪些系统库（Electron 的库多为启动时 dlopen，ldd 查不出来）
ldd /usr/local/lib/hermes-agent/apps/desktop/release/linux-arm64-unpacked/hermes | grep 'not found'
ldconfig -p | grep -E 'libgtk-3|libnss3|libgbm|libatspi'
```

- **`error while loading shared libraries`** → 装系统包：
  CentOS/Kylin 系 `sudo yum install -y gtk3 nss nspr libdrm mesa-libgbm
  alsa-lib atk at-spi2-core cups-libs libxkbcommon pango cairo xdg-utils`；
  UOS/Debian 系见 `check-env.sh` 输出里那条 `apt install`。
- **`The SUID sandbox helper binary was found, but is not configured correctly`**
  → `chrome-sandbox` 需要 `root:4755`：

  ```bash
  sudo chown root:root .../linux-arm64-unpacked/chrome-sandbox
  sudo chmod 4755 .../linux-arm64-unpacked/chrome-sandbox
  ```

  不想动 setuid 也行 —— 上游会自动补 `--no-sandbox`。
- **`Missing X server or $DISPLAY`** → 这台机器没有图形会话。
  改用 `hermes dashboard` + 浏览器，体验基本等价。
